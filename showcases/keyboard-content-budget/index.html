The pain

A bottom-anchored CTA is the right call at rest — it is thumb-reachable and always available. But the soft keyboard takes 40–62% of the screen, and neither the header nor the CTA gives anything back. Content is squeezed from both ends until the user is typing into a field whose label and hint are off-screen, with the next field clipped behind a button they do not need yet.

The rule: a content budget

Chrome is the thing that yields. Declare an invariant — the scrollable content region never drops below 45% of the visible viewport — and degrade the chrome in a defined order until it holds. Each rung is re-measured before the next is tried, so you only ever give up as much as you have to:

  • L0 — everything at full size, CTA pinned. Keyboard closed, or open with room to spare.
  • L1 — the CTA leaves the shell and flows to the end of the form, reached by scrolling. Spent first: it is the biggest saving and the cheapest, because while the keyboard is open the button's job is already covered by the keyboard's own next/done key. It returns the moment the keyboard closes.
  • L2 — the header compacts as well (subtitle, step labels and section tab drop, logo shrinks). Spent last — knowing which step you are on is worth more than a button you can scroll to.

Where to put the bar

Not position: fixed, and not position: sticky either. The CTA here is a flex row of the app shell, a sibling of the scroll region:

.app { display: flex; flex-direction: column } → .appbar (flex:none) · .scroll (flex:1, overflow:auto) · .ctabar (flex:none)

It is therefore always visible regardless of scroll position, it never covers content (the scroll region is sized to exclude it), and it sidesteps iOS's displacement of fixed elements. “Leave the shell” at L3 is then just moving that one node into the scroll region.

How the keyboard is measured

CSS cannot see the keyboard. 100vh, 100dvh and 100svh are anchored to the layout viewport, which iOS Safari does not shrink when the keyboard opens. The only reliable signal is window.visualViewport:

kb = innerHeight − visualViewport.height − visualViewport.offsetTop

Two things that are easy to miss

Pin the page. iOS scrolls the layout viewport to reveal the focused input. A shell fixed to that viewport gets dragged with it, and its bottom row — the CTA — slides off screen, so the button appears and disappears depending on page scroll. Since the shell owns its own scrolling, keep the page itself at scrollY = 0.

Never animate what you measure. This shell used to carry transition: bottom .18s. The budget then measured the height the shell had before the keyboard opened, concluded there was plenty of room, and stayed at L0 — reproducing the original pain in code that reported success. It only showed up when a human toggled the keyboard, never on page load. You don't need the transition: visualViewport fires resize continuously as the keyboard slides, so an untransitioned shell tracks it smoothly for free.

Bring the field into the preserved region. A guaranteed content region only helps if the focused field lands inside it — so on focus, wait for the keyboard animation to settle, re-measure, then scroll the field (with its label and hint) to the centre of the content region.
